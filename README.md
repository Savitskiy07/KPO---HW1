# HW1 — «ВышКат»

Учебное консольное приложение учёта имущества кикшеринга на C++17.
Реализованы доменная модель, техосмотр, учёт транспорта и вещей,
специализированный DI-контейнер, интерактивный ввод и поведенческие тесты.

## Возможности

| Команда | Операция |
|---|---|
| `1` | Добавить велосипед или электросамокат через техосмотр |
| `2` | Добавить шлем или зарядную станцию |
| `3` | Показать количество транспорта, вещей, всего имущества и суточную энергию |
| `4` | Показать транспорт для новичков с простотой не ниже 6 |
| `5` | Показать имена и инвентарные номера всего принятого имущества |
| `0` | Завершить работу |

Все данные вводит пользователь. Демонстрационные объекты не создаются в рабочем коде.
После операции приложение возвращается в меню. Ошибочный ввод повторяется для того же
поля; EOF завершает работу без добавления незавершённого объекта.

## Инструменты, сборка и запуск

- C++17, CMake 3.20 или новее, компилятор и подходящий генератор сборки.
- Основная среда разработки: CLion на Windows со встроенным MinGW.
- doctest 2.4.11 включён в [third_party/doctest](third_party/doctest/).
  Заголовок и лицензия сохраняются; скачивать библиотеку при сборке не требуется.
- Цели приложения и тестов: `HW1` и `HW1_tests`.
- Python и gcov нужны только для отдельного измерения покрытия, не для приложения.

Команды из корня проекта, например для Linux с Make или Ninja:

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build --target HW1 HW1_tests
ctest --test-dir build --output-on-failure
./build/HW1
```

Тесты можно запустить непосредственно: `./build/HW1_tests`.
CTest содержит одну запись `setup_test`, которая запускает весь `HW1_tests`,
а не только тест настройки. В текущем комплекте doctest: 73 теста и 559 проверок.

### CLion и MinGW

1. Открыть корневой [CMakeLists.txt](CMakeLists.txt) как проект.
2. Выбрать профиль CMake с toolchain MinGW; добавить `-DBUILD_TESTING=ON`.
3. Сохранить исходники в UTF-8 и выполнить Reload CMake Project.
4. Собрать и запустить `HW1_tests`, затем `HW1`.
5. Ввести сценарий ниже и проверить русские имена и сообщения.

Для сборки MinGW вне IDE нужны `g++`, `mingw32-make` и DLL среды MinGW в `PATH`:

```powershell
cmake -S . -B build-mingw -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON
cmake --build build-mingw --target HW1 HW1_tests
ctest --test-dir build-mingw --output-on-failure
.\build-mingw\HW1.exe
```

Для многоконфигурационного генератора, например Visual Studio, при сборке используют
`--config Debug`, при запуске CTest — `-C Debug`; исполняемые файлы находятся
в подкаталоге `Debug`. Это инструкция, а не подтверждение проверки MSVC.

В CMake сохранены `/utf-8 /Zc:__cplusplus` для MSVC и флаги UTF-8 для GCC.
[main.cpp](src/main.cpp) на Windows задаёт кодовые страницы UTF-8 под `#ifdef _WIN32`.
В CLion на Windows проверены работа меню, русский ввод и основной сценарий.
На другой машине отображение также зависит от терминала и настроек IDE.

## SOLID и границы применения

- **SRP.** [Vehicle](src/domain/Vehicle.cpp) проверяет доменное ограничение простоты;
  [ServiceCenter](src/services/ServiceCenter.h) принимает решение техосмотра;
  [FleetService](src/services/FleetService.cpp) ведёт учёт;
  [ConsoleApp](src/console/ConsoleApp.cpp) взаимодействует с пользователем.
  Повторная проверка диапазонов в консоли позволяет повторить ввод и не отменяет
  проверок конструкторов. Консоль не вычисляет энергию и не проверяет дубликаты сама.
- **OCP.** [FleetService](src/services/FleetService.cpp) суммирует энергию через
  `dynamic_cast<const EnergyConsumer*>`, а не перечислением конкретных классов.
  Фильтр новичков использует свойство `Vehicle`. Новый совместимый тип может участвовать
  в этих расчётах без их переписывания.
- **LSP.** [Bicycle](src/domain/Bicycle.h) и [ElectricScooter](src/domain/ElectricScooter.h)
  используются через `Vehicle`, а вещи — через `Item` и `InventoryItem`.
  Конкретные классы сохраняют ограничения базовой модели; потребители энергии
  возвращают конечный неотрицательный расход. Виртуальные деструкторы позволяют
  корректно уничтожать объекты через базовые указатели.
- **ISP.** [InventoryItem](src/domain/InventoryItem.h),
  [EnergyConsumer](src/domain/EnergyConsumer.h) и
  [InspectionService](src/services/InspectionService.h) имеют небольшие отдельные
  контракты. Для шлема не нужен метод энергии, а для вещи — метод техосмотра.
- **DIP.** [FleetService](src/services/FleetService.h) получает
  `const InspectionService&`, не создаёт `ServiceCenter` и не обращается к контейнеру.
  [AppContainer](src/composition/AppContainer.cpp) выбирает реализацию и внедряет её.
  Тесты передают собственные реализации того же интерфейса.

**Наиболее явно выражен DIP:** бизнес-сервис работает с абстракцией техосмотра,
а его решение меняется подменой зависимости без изменения `FleetService`.

**Сознательно ограничен OCP в консольном выборе типов:**
[ConsoleApp::addVehicle/addItem](src/console/ConsoleApp.cpp) знает четыре конкретных вида.
При добавлении вида потребуется изменить выбор и создание объекта в меню, добавить
тесты и при необходимости исходник в CMake. Для небольшой программы это приемлемо:
универсальные фабрики, реестр типов и система плагинов здесь не нужны.
Проект не объявляется полностью закрытым для любых изменений.

## Как повлияют расширения

| Изменение | Что потребуется |
|---|---|
| Новый транспорт | Класс-наследник `Vehicle`, при потреблении энергии — также `EnergyConsumer`; выбор в консоли, тесты, при необходимости запись в CMake. Учёт и отчёты сохраняются, если подходят существующие контракты и правило техосмотра. Новые правила требуют изменения или подмены техосмотра. |
| Сотрудник | Отдельная модель и сервис учёта персонала, при необходимости новые команды. По ТЗ сотрудник не является имуществом на балансе, поэтому не наследует `InventoryItem` и не добавляется в `FleetService`. |
| Склад запчастей | Отдельный модуль для складских остатков и операций. Штучную инвентаризируемую вещь можно представить через `Item`, но количества расходников и складские операции не следует искусственно сводить к одному объекту имущества. Новые отчёты, меню и связи потребуют изменений. |

Эти расширения сейчас не реализованы.

## DI-контейнер, владение и время жизни

[AppContainer](src/composition/AppContainer.h) — специализированный контейнер приложения,
не универсальный DI-фреймворк. Стандартный конструктор создаёт `ServiceCenter`.
Другой конструктор принимает `unique_ptr<InspectionService>` и отклоняет `nullptr`
через `std::invalid_argument` до разыменования.

Контейнер владеет техосмотром через `unique_ptr`, а `FleetService` хранит непосредственно
как поле. Он создаёт сервис парка с выбранным техосмотром; каждый вызов
`getFleetService()` возвращает ссылку на тот же экземпляр. Два контейнера независимы.

В [объявлении полей](src/composition/AppContainer.h) `inspection_` стоит перед `fleet_`.
Поля уничтожаются в обратном порядке: сначала парк и его имущество, затем техосмотр.
Копирование и перемещение контейнера запрещены. Полученная ссылка на парк не должна
использоваться после уничтожения контейнера.

Сам `FleetService` не владеет переданным техосмотром: при отдельном создании сервиса
вызывающий код обеспечивает достаточное время жизни зависимости. В
[main.cpp](src/main.cpp) контейнер существует всё время работы `ConsoleApp`.

## Правила и допущения

Порог новичков `>= 6` и шкала 1–10 заданы в ТЗ. Детали ниже фиксируют выбранную
реализацию и не выдаются за дословные требования преподавателя.

- Техосмотр принимает транспорт при исправных тормозах и неповреждённой раме.
  Признаки вводит пользователь; реальную диагностику программа не моделирует.
  Вещи не проходят техосмотр.
- Номера уникальны среди всего принятого имущества. Сравнение точное строковое:
  `001` и `1`, `abc` и `ABC`, `ABC` и ` ABC ` — разные номера.
  Регистр и пробелы в непустых номерах сохраняются; имена также не обрезаются.
- Пустые и состоящие только из пробельных символов имя и номер отклоняет консоль.
  Доменные конструкторы не добавляют такой проверки и не нормализуют строки.
- Дубликат транспорта отклоняется до техосмотра. Отказ техосмотра не занимает номер.
  Отклонённый объект не попадает ни в количество, ни в энергию, ни в списки.
- `addVehicle` и `addItem` принимают `unique_ptr` по значению: при успехе владение
  сохраняется в коллекции, при отказе переданный объект уничтожается.
  Пустой указатель вызывает `std::invalid_argument`.
- Расход задаётся в кВт·ч за сутки: конечное неотрицательное число, включая ноль.
  Дробный разделитель при вводе — точка. Суммируются все принятые потребители,
  включая зарядные станции. Передача энергии и процесс зарядки не моделируются.
- Хранение только в памяти; при завершении процесса данные теряются.
- Новички перечисляются в порядке добавления транспорта. Общий инвентарь содержит
  сначала транспорт, затем вещи; внутри каждой группы сохраняется порядок добавления.
- Списки возвращаются как `vector<InventoryEntry>` по значению: это снимки данных,
  а не передача владения объектами.
- `false` от `addVehicle` не раскрывает причину: консоль пишет
  «Отказ: номер уже занят или техосмотр не пройден». Повторного техосмотра нет.
  При `false` от `addItem` выводится «Отказ: номер уже занят».
- При EOF частично введённый объект не создаётся; ранее принятые объекты остаются
  в сервисе до его уничтожения. Неожиданные ошибки сервисов не маскируются как ошибки ввода.

Ожидаемые результаты по порядку:

4. Отчёт: транспорт — `2`, вещи — `2`, всего — `4`, суточная энергия — `3.65` кВт·ч.
5. Список новичков содержит только `Учебный самокат | E001`:
   велосипед имеет простоту `5`, вещи в этот список не входят.

   | Название | Номер |

   | Учебный самокат | `E001` |
   | Защитный шлем | `H001` |

об отсутствии объектов. Эти случаи также проверяются тестами.

## Воспроизводимое покрытие GCC/gcov

Метрика — **покрытие исполняемых строк**, которые gcov относит к собственному C++ коду
тестовой сборки. Строка считается покрытой, если её счётчик больше нуля хотя бы в одной
единице компиляции. Повторения одной строки заголовка объединяются по пути и номеру,
поэтому она не учитывается несколько раз. Непокрытые исполняемые строки остаются
в знаменателе; комментарии и прочие неисполняемые строки не входят в него.
Это не покрытие ветвей, условий, функций или всех возможных сценариев.

Включены `.cpp` и `.h` из `src/domain`, `src/services`, `src/composition`, `src/console`,
для которых gcov создал записи. Исключены `src/main.cpp`, его Windows-ветка,
`tests`, `third_party`, стандартная библиотека и инструменты из `tools`.
Следовательно, процент не характеризует всё приложение вместе с точкой входа.

Нужны GCC и соответствующий ему gcov с поддержкой `--json-format` (GCC 9+),
а также Python 3.8+. Для измерения использовались GCC/gcov 13.3 и Python 3.12.
Использовать `g++` и `gcov` из одной установки; в Windows каталог MinGW `bin`
также должен быть в `PATH`, чтобы запускался тестовый `.exe`.
MSVC для этого способа не подходит. gcovr не требуется.

Из корня проекта:

```sh
python3 tools/coverage.py --cxx g++ --gcov gcov
```

В Windows при установленном Python:

```powershell
py -3 tools/coverage.py --cxx g++ --gcov gcov
```

Параметры `--cxx` и `--gcov` допускают полные пути к соответствующим `.exe`.
Скрипт не меняет обычную сборку CMake. Он отдельно компилирует все `.cpp` четырёх
указанных каталогов и `tests` с `-std=c++17 -O0 -g --coverage`, предупреждениями
`-Wall -Wextra -Wpedantic` и флагами UTF-8; линкует с `--coverage`, запускает тесты,
затем `gcov --json-format` для каждой единицы компиляции.
Тесты инструментируются, чтобы учесть используемый из них код заголовков,
но сами тестовые строки исключаются из отчёта.

Каждый запуск создаёт новый `build-coverage/run-*`; прежние счётчики не смешиваются.
Скрипт останавливается при ошибке сборки, тестов или gcov и не выдаёт неполный процент.
В каталоге успешного запуска находятся:

- `coverage-summary.json`: общий результат, результаты по файлам и номера непокрытых строк;
- `compiler.log`, `tests.log`, `gcov.log`: диагностические журналы;
- объектные файлы, `.gcno`, `.gcda`, исходные JSON-отчёты gcov и тестовый исполняемый файл.

работу консольного меню, ввод и отображение русского текста, а также основной
сценарий работы: добавление транспорта и вещей, прохождение и отказ в
техосмотре, обработку повторяющихся инвентарных номеров, отчёт о количестве
имущества и суточном энергопотреблении, список транспорта для новичков и
общий инвентарный список. При выполнении этих сценариев ошибок не обнаружено.

**Автоматизированная проверка.** В отдельной среде с GCC/gcov 13.3
успешно выполнены **73 юнит-теста и 559 проверок**. Измерение через
`python3 tools/coverage.py --cxx g++ --gcov gcov` дало результат
**265 из 273 исполняемых строк (97,07%)** в указанной области покрытия.

В измерение вошли `.cpp` и `.h` из `src/domain`, `src/services`,
`src/composition` и `src/console`; не вошли `main.cpp`, тесты, сторонние
библиотеки и инструменты. Восемь непокрытых строк относятся к обработчикам
`std::invalid_argument` в `ConsoleApp`: пользовательский ввод проверяется
до вызовов конструкторов. Метрика показывает покрытие исполняемых строк,
а не ветвей или всех возможных сценариев.

Повторное измерение покрытия с MinGW на Windows не проводилось;
приведённый результат получен с GCC/gcov 13.3 в отдельной среде.
Отдельный итоговый запуск CTest на Windows и проверка сборки
компилятором MSVC также не подтверждены.
